# Cross-Repo Work

`new-worktree` creates worktrees at `~/Projects/.worktrees/<repo>/<branch>` — a shared directory outside any individual repo, rather than nested inside one. That's deliberate: a session's file and shell access is scoped to the root it was launched or rooted in, and the normal case here is a session rooted at `~/Projects` itself (the parent of every repo). Because `~/Projects` is the one directory every repo shares, a worktree stored there is reachable from a `~/Projects`-rooted session no matter which repo it belongs to.

When a task needs changes in a repo other than the one you started in, treat it exactly like the first: `builtin cd` into that repo's root, run `new-worktree <branch>` there, and work the normal worktree/commit/PR flow inside it — independently of whatever's happening in the first repo's worktree. Each touched repo ends up with its own branch, commit history, and PR; there's no single cross-repo PR.

**The one remaining edge case:** a session rooted *inside a single repo* rather than at `~/Projects` (this mostly bites background jobs launched against one specific repo, e.g. a job rooted in `agent-tasks` that picks up a task tagged `--project songbird`) still can't reach `~/Projects/.worktrees` — that path falls outside its own root, and a subagent spawned via the `Agent` tool from within such a job inherits the same restriction rather than getting a fresh, independently-rooted session. If you hit this:

- **Don't work around it.** Don't try raw absolute-path edits into a manually-created worktree of the other repo — a session outside its own root risks colliding with other agents working in that repo even where the filesystem happens to be reachable.
- **Create a task instead**, via `atask add`, with enough detail that a session actually rooted in the target repo (or at `~/Projects`) can act on it without re-deriving your investigation: the target repo/app, relevant files (with line numbers), the concrete change to make, and any conventions or gotchas discovered along the way. Tag it `--project <target-repo>`.
- If the investigation surfaced durable knowledge (an architecture pattern, a constraint) and you can reach the target repo read-only, write it into that repo's `AGENTS.md`/`DOMAIN.md` directly — but the actual code change goes through a task, not a workaround.
- If you were holding a claim on a task that turned out to need this handoff, don't just `atask release` it — that puts the original, under-detailed task text back on the open queue, where another agent could claim it without the detail you've since worked out. Instead, file the fully-detailed follow-up task(s) that together cover the original's scope (reference the original task's id in the new one for traceability), then mark the original complete with `atask done <id>`. The follow-up task(s) *are* the original's scope now — completion here means "investigated and properly handed off," not "implemented."
