## Before making a repo public

A repo going public needs review beyond just "no secrets" — secrets are the obvious case, but personal and organizational specifics leak just as easily and don't get caught by a credentials grep. Check all of these, not just the tracked files as they currently stand:

- **Commit history, not just current file content.** `git log --all -p` can carry things that were later edited or removed from the working tree but never purged from history — same for author name/email (`git log --all --format="%an <%ae>"`). Fixing history means `git filter-branch` (or `git-filter-repo`) followed by a force-push; coordinate with the user before either, since force-pushing rewrites what's already on the remote.
- **PR and issue bodies, not just code.** These are public GitHub content once the repo is public, same as any tracked file — real device names, specific data from a private test run, or internal task-tracking references (ticket IDs, tool names) don't belong in a PR/issue body meant for public eyes.
- **Personal identifiers.** A GitHub handle in `manifest.json`'s `codeowners` (or similar per-project convention) ties the repo to a specific person. If the project has an owning GitHub org, prefer the org handle there instead of an individual's — still satisfies whatever tooling requires the field (e.g. Home Assistant's `hassfest` requires `codeowners` to be present and non-empty for a custom integration, but doesn't care whose handle it is).
- **Private infrastructure details.** Specific IPs/hostnames on a private network, SSH access details (`user@host`, key paths), and references to other repos' existence or visibility (private repo names, self-hosted CI runner setups and their security policies) don't belong in public content. State only what the code itself actually needs (e.g. a config flow that takes `host` as user input doesn't need the real host documented anywhere in the repo).
- **CI workflow comments are public content too.** A code comment explaining *why* a workflow uses GitHub-hosted runners instead of an org's usual self-hosted ones reveals that self-hosted runners exist at all, and potentially their security configuration — say what the workflow does, not why it differs from private infrastructure the public has no reason to know about.

Do a full sweep (grep the working tree AND `git log --all`) rather than just fixing the one thing that prompted the review — these issues cluster, and finding one is a good reason to check for siblings.

## Rewriting pushed history

After `git filter-branch` (or `git-filter-repo`) rewrites commits that are already on the remote, `git push --force-with-lease` can spuriously reject with "stale info" — filter-branch also rewrites the local `refs/remotes/origin/*` tracking refs to the new history, so `--force-with-lease`'s safety check has nothing accurate left to compare against. Plain `git push --force` is the correct fix here, not a sign something else is wrong — safe specifically because you just rewrote this history yourself moments ago and know exactly what's being overwritten.

## Self-hosted runners for private repos

Private `rn-ax` repos run their CI on the Contabo self-hosted runners rather than GitHub-hosted `ubuntu-latest` — public repos get free GitHub-hosted minutes and have no reason to move, but a private repo meters Actions minutes with no such allowance, while the Contabo boxes' own capacity otherwise sits idle. This also sidesteps a specific pain point: a GitHub-hosted runner has no route to any home-LAN service, so CI that needs one has to go through a public, often Access-gated hostname (proxy scripts, service tokens, and all the fragility that brings); Contabo already has a direct path to TrueNAS over Cloudflare WARP, so the same CI job just works with no extra network layer. See the `contabo-hosts` skill for the actual box inventory, connectivity details, and the runner registration procedure — this section covers the org-level conventions and the incident that shaped them.

## Self-hosted runner: stuck job dispatch

A self-hosted runner can silently stop accepting jobs from the queue while still reporting `online`/`busy: false` via `GET /orgs/<org>/actions/runners` and logging "Listening for Jobs" — new jobs (even a completely fresh `workflow_dispatch` run with no dependency on anything else) sit in `queued` indefinitely, never reaching a runner, with no error anywhere. Confirm it's not a genuine network/config problem first: check that the runner host can actually reach the broker URL in `.runner`'s `serverUrlV2` (a plain `curl` should respond in well under a second) and that org/repo Actions settings and runner-group visibility all look correct. If all of that checks out and jobs still won't dispatch, the runner's own diagnostic log (`_diag/Runner_*.log`, the newest one for the current process) is the next thing to check — ours went completely silent after "Set runner/worker IPC timeout to 30 seconds," no further lines at all, not even a repeating poll message.

Several `actions/runner` issues describe the same high-level symptom — stuck queue despite an online/idle runner — without a confirmed root cause from GitHub staff: [#3371](https://github.com/actions/runner/issues/3371) (whose reporters saw a distinct repeating log line, "BrokerMigration message received. Polling Broker for messages..." — check for that exact string before assuming it's the same bug, since a silent log doesn't match it), [#3478](https://github.com/actions/runner/issues/3478), and [#4312](https://github.com/actions/runner/issues/4312) (a different variant where the runner shows *busy* from a hung worker process rather than genuinely idle). Treat these as evidence this class of problem is real and known, not as a confirmed diagnosis for a given instance — verify against the actual log content rather than pattern-matching on symptoms alone.

Two escalating fixes, in order, tried in a real incident and neither one guaranteed:
1. **Restart the runner service** (`sudo systemctl restart actions.runner.<org>.<name>.service`). Several of the linked issues report this as sufficient on its own.
2. **Fully re-register the runner** if a restart alone doesn't get a fresh test job past `queued` within a minute or two. Stop the service, move aside `.runner`, `.runner_migrated` (if present — appears when GitHub migrates a runner's connection onto its newer protocol; harmless to move aside either way), `.credentials`, and `.credentials_rsaparams` (don't delete outright — keep them until the new registration is confirmed working), then re-run `./config.sh --url <org-url> --token <fresh-registration-token> --name <same-name> --labels <same-labels> --unattended --replace` as the runner's own user. `--replace` handles a same-named runner already existing server-side, so this doesn't require a separate removal step first, and keeps the same runner ID rather than allocating a new one. A fresh registration token comes from `POST /orgs/<org>/actions/runners/registration-token` (expires in ~1h, and is reusable for registering multiple runners within that window). Restart the service afterward and verify with a throwaway `workflow_dispatch` run before trusting it for anything real.

In one real incident, both fixes above left the runner's diagnostic log looking identical before and after (clean broker session, then silence) — including after a full re-register that got a fresh credentials file but kept the same runner ID via `--replace`. That pointed at something stuck server-side on GitHub's end specific to the **org-level** runner pool.

**The fix that actually worked: re-register as a repo-level runner instead of an org-level one**, confirmed live and matching a workaround reported in [this comment on #3478](https://github.com/actions/runner/issues/3478#issuecomment-2390552416) — an org-level runner can get stuck this way while a repo-level runner on the exact same host picks up jobs immediately. To convert an existing install from org-level to repo-level on the same box (rather than provisioning a new one):
1. Deregister the old org-level entry so it doesn't linger as a dead entry: `gh api -X DELETE orgs/<org>/actions/runners/<id>`.
2. Stop the service and uninstall its systemd unit (the unit name is scope-specific, e.g. `actions.runner.<org>.<name>.service`): `sudo systemctl stop <service>`, then `sudo bash -c 'cd /opt/github-runner && ./svc.sh uninstall'`.
3. Clear local registration state: `sudo -u github-runner bash -c 'cd /opt/github-runner && rm -f .runner .credentials .credentials_rsaparams'`.
4. Get a **repo-scoped** registration token (different endpoint from the org one): `POST /repos/<org>/<repo>/actions/runners/registration-token`.
5. Register against the repo URL instead of the org URL: `./config.sh --url https://github.com/<org>/<repo> --token <repo-token> --name <same-name> --labels <same-labels> --unattended --replace`.
6. Reinstall and start the service (its unit name changes too, e.g. `actions.runner.<org>-<repo>.<name>.service`): `sudo bash -c 'cd /opt/github-runner && ./svc.sh install <service-user> && ./svc.sh start'`.

The tradeoff: a repo-level runner only serves that one repo, not the whole org, so this isn't free if other repos were relying on the same shared org-level pool — provision/convert enough runners to cover them, or accept that repo gets dedicated capacity going forward.

## Verify credentials on a new or newly-deployed repo

A new repo's CI can look fully green while its actual deploy step silently no-ops or crashes, because the job that needs a secret runs last and the earlier jobs (lint, tests, validation) pass regardless of whether that secret exists. `secrets: inherit` from a caller to a reusable workflow only passes through what's actually visible to the caller; a name the callee expects but the caller can't see resolves to an empty string, not a missing-secret error — the failure surfaces later, inside whatever script tries to use that empty value (e.g. a URL parse crashing on a string with no `://` in it), not at the point secrets are resolved.

A secret several repos share (e.g. credentials for one shared external service several CI workflows all talk to) belongs at the **org level** (`gh secret set NAME --org <org> --visibility selected --repos repo1,repo2`), not duplicated as an identical repo-level secret on each one — a repo-level secret of the same name always wins if both exist, so pick one location and delete the other rather than letting both linger. This doesn't eliminate the "new repo missing it" failure mode, it just moves the fix to one place: adding a new repo to the org secret's `--repos` list, rather than recreating the secret's value from scratch on each new repo. Check what's actually configured with `gh secret list --repo <owner>/<repo>` (repo-level) and `gh secret list --org <org>` plus `gh api orgs/<org>/actions/secrets/<name>/repositories` (which repos an org-scoped secret is actually visible to) — comparing a new repo's visibility against a sibling that already works catches a repo that was simply never added to the list.

**Org-level secrets don't reach private repos on GitHub's Free plan**, no matter what the secret's visibility is set to (even "All repositories") — the workflow run just sees an empty string for that secret, no error anywhere. `gh api orgs/<org> --jq .plan.name` shows the plan. If a private repo's CI needs a credential and the org is on Free, set it as a repo-level secret on that repo instead of (or in addition to) the org one — this bit `rn-ax/workers` (private, org on Free) directly: an org secret set with visibility "all" still resolved empty in every run until moved to a repo secret.

When the secret is a URL for something on a private network, confirm it's reachable from where the workflow actually runs, not just from your own machine — a GitHub-hosted runner has no route to a private LAN IP, so a "works when I curl it" URL still fails in CI unless it's the service's public/remote address instead.

## Maintaining a fork with local changes

**Before forking anything, scan the repo for security holes** — both in general and specifically for what forking it exposes to this org. Grep the tree (not just the integration's own directory — dev scripts, devcontainer config, CI files too) for `eval(`/`exec(`/`subprocess`/`os.system`/`pickle.`/`marshal.`/dynamic imports/curl-or-wget-pipe-to-shell patterns, check what runtime dependencies actually ship (a HA custom integration's `manifest.json` `requirements` key is what lands on the live instance — a `requirements.txt` at repo root is normally dev-only tooling, don't conflate the two), and check whether any CI workflow that will keep running on this fork (or that gets replaced — see below) could expose org secrets to an untrusted PR (a `deploy`-type job gated on `github.ref == 'refs/heads/main'` only ever runs on a push after a human merges, never on an incoming `pull_request`; a workflow using `pull_request_target` with secrets and no equivalent gate is the pattern to watch for). Do this before wiring the fork into anything that grants it real access (org secrets, a live instance, deploy credentials), not after.

Before forking a repo to add a feature or fix upstream doesn't have, check whether upstream already covers it or has an open issue/PR for it (`gh issue list`/`gh pr list --repo <upstream>`, and read the actual issue thread — a maintainer comment like "working as intended" on a duplicate tells you whether it's worth waiting on). Only fork once that's confirmed absent.

**Document the fork's reason and its drop condition at the top of the README**, not in a separate file — a README is what a reader actually opens; a bespoke `FORK.md` isn't a recognized GitHub convention the way `LICENSE` or `CONTRIBUTING.md` are, so it goes unread. Use a `> [!IMPORTANT]` callout right under the title: why the fork exists (linking the upstream issue that would obsolete it), the condition under which to drop it and switch back to upstream, and a concise list of every change from upstream — update that list whenever the diff changes, so it stays a reliable summary instead of prose that rots.

**Keep fork-specific logic in its own module** (a generic name like `_fork.py`, not org- or repo-specific — the pattern should be copyable to the next fork without inventing a new name each time) rather than inlined across the upstream files, and have the upstream files import and call it at as few, minimal call sites as possible. This isn't just tidiness — it directly shrinks what a future `git merge upstream/main` has to reconcile line-by-line, since upstream's own commits are far less likely to touch a file that doesn't exist upstream at all. The same applies to any tests added for the fork-specific behavior: put them in their own file rather than editing upstream's existing test files, if upstream has any. A constant that has to point somewhere real (e.g. a docs URL shown in the UI) legitimately references the fork's own repo/org — that's a functional necessity, not identity-stamping — but don't bake the org/repo name into names, filenames, or module paths where a generic one works identically.

**Every line touched in an upstream file is a future merge-conflict candidate — don't touch a line unless the fork's actual feature requires it.** It's easy to pick up unforced changes along the way (a version bump, a metadata field, a URL that "should" point at the fork) without noticing they're optional. Before committing, diff against upstream's matching commit (`git diff <upstream-ref> -- <file>`) and justify every changed line against the feature being added, not general tidiness. Concretely: don't bump a version field nothing in the fork's own CI consumes (check what actually reads it before bumping — a `manifest.json` version field that only mattered to a release workflow you're deleting anyway consumes nothing); don't touch a constant/URL/label that isn't referenced anywhere (dead code costs nothing to leave as upstream had it, and a diff on it buys nothing); do keep a change that's a direct, unavoidable consequence of the feature itself (e.g. a field that must become optional because another field it depended on became optional) — the test is "does the feature actually require this line to differ," not "would this be nicer."

**Renovate doesn't keep a fork in sync with upstream** — its job is bumping versions declared in dependency manifests/lockfiles within a repo, not merging unrelated git history from another repo. For that, add a scheduled GitHub Actions workflow, owned by the fork itself, that fetches upstream's default branch and opens a PR merging it in (a human reviews and merges, same as any other PR — never push straight to main or force-reset it). Don't reach for the `wei/pull` GitHub App for this: it's not a composable `uses:`-able Action (there's no `action.yml`, just an installable-via-marketplace bot), it requires a manual org-level app install, and its default sync behavior is a **hard reset** to upstream that silently discards the fork's own commits unless `.github/pull.yml` is carefully configured otherwise — a real risk for a repo that carries actual local changes, not just a same-as-upstream pointer fork.

**Rebuild `.github/` around this org's own conventions rather than carrying forward upstream's.** A small single-purpose fork doesn't need upstream's full community/release apparatus — release-drafter, a release-on-tag workflow, issue templates, a PR-label-requirement bot, `.github/settings.yml` tuned for a community project — that's overhead for a fork nobody but this org uses. For a Home Assistant integration specifically, replace upstream's CI with the existing `rn-ax/poppycock` reusable workflow (`ha-integration-ci.yml`: hassfest + hacs + deploy-to-HACS) the same way `ha-gym-tracker` uses it, add the new repo to the `HOME_ASSISTANT_URL`/`HOME_ASSISTANT_TOKEN` org secret's repo list, and keep `hacs.json` pointing HACS at `main` directly (no `zip_release`) rather than upstream's tag-triggered zip-release flow. Replace `dependabot.yml` with a `renovate.json` extending `poppycock`'s preset (see Org conventions below) rather than keeping upstream's dependabot config — this org standardizes on renovate. This still needs applying per-fork — don't assume it's already done just because the pattern is documented here.

A `hacs/action` check can fail for reasons that have nothing to do with the integration's correctness. `rn-ax/poppycock`'s `ha-integration-ci.yml` exposes a `hacs_ignore` input for exactly this (`with: hacs_ignore: "brands issues"` — space-separated, per `hacs/action`'s own syntax — from the calling repo's `ci.yml`) rather than blocking CI. Every `rn-ax` HA integration repo needs `issues` in that list unconditionally: `hacs/action`'s own publish validation requires `has_issues` enabled, which directly conflicts with this org's Issues-disabled-everywhere policy (see below) — that's a permanent mismatch to skip past, not a one-off. `brands` is conditional: only add it for a domain with no entry yet in `home-assistant/brands` (an established integration like `ha-healthchecksio` already has one and doesn't need it) — check what the failure actually says before assuming both are needed.

## Org conventions

- **`rn-ax` org repo naming.** A repo under the `rn-ax` GitHub org carries no `rn-` prefix in its GitHub name (e.g. `rn-ax/workers`), but is cloned locally with an `rn-` prefix on the directory name (e.g. `~/Projects/rn-workers`). When creating a new repo in this org, name it without the prefix on GitHub and clone it into a prefixed local directory.
- **A Home Assistant integration repo carries an `ha-` prefix on GitHub itself** (`ha-gym-tracker`, `ha-inteno-router`, `ha-fork-status`, `ha-healthchecksio`) — this is a separate, additional prefix layered on top of the general org-naming rule above, specific to this one repo category. It applies to a fork of an externally-named upstream too: `custom-components/healthchecksio` became `rn-ax/ha-healthchecksio`, not `rn-ax/healthchecksio`, once it had this org's own feature work in it. Renaming an existing repo to add this prefix needs a few follow-ups beyond the GitHub rename itself (GitHub's redirect keeps the old name resolving, so these are easy to miss): `.github/settings.yml`'s `repository.name` field (else the Settings app renames it back to the old name on its next sync), any self-referential URL in the integration's own `manifest.json` (`documentation`, `issue_tracker`) or fork-specific module (a `DOCS_URL`-style constant), and the local clone directory name.
- **Every `rn-ax` repo has a `.github/settings.yml` extending `poppycock`.** If the org uses a `.github/settings.yml` (the GitHub Settings app) with `_extends: <base-repo>`, config in the base merges with each repo's own overrides — including array keys like `branches:` and `labels:` (matched by `name`), not just simple `repository:`-level keys. A repo's own settings.yml only needs to state what's actually specific to it (`name`, `description`) plus anything it wants to override; don't duplicate what the base already covers — in particular, don't restate `has_issues: false`, since `poppycock`'s base already sets it (see below) and every repo should inherit that, not override it back to `true`. **Check the repo's actual current visibility (`gh api repos/<org>/<repo> --jq .private`) before writing `private: false` or `true`** — the Settings app enforces whatever this file says on its next sync, so copying a `private: false` line from a sibling repo's settings.yml (e.g. a public HACS integration) onto a repo that's genuinely meant to stay private (internal infra, nothing HACS-shaped requiring public visibility) would actually flip its visibility. `poppycock`'s base template already defaults to `private: true`; a repo that's supposed to be private doesn't need a `private:` line in its own settings.yml at all.
- **Issues stay disabled org-wide, even where that conflicts with a tool's own expectations.** This org tracks work in `atask`, not GitHub Issues — `poppycock`'s base `.github/settings.yml` sets `has_issues: false` for exactly this reason, and no repo's own settings.yml should override it to `true`, even when something external assumes Issues are on. Two known conflicts, resolved the same way (work around the tool, don't re-enable Issues): `hacs/action`'s publish validation hard-requires `has_issues` (see `hacs_ignore: issues` above); a Home Assistant integration's `manifest.json` `issue_tracker` field is surfaced by HA's UI as a "report an issue" link to real end users, and with Issues disabled that link 404s — there's no clean fix for this second one yet (a redirect page, pointing it elsewhere, or accepting the dead link are all real options), so flag it rather than silently picking one when it comes up.
- **Every repo has a `mise.toml`, and CI provisions tools through it, not a language-specific setup action** — not just Python repos: a Node/TypeScript repo (e.g. `rn-ax/workers`) declares `node` in `[tools]` the same way, and its CI's `jdx/mise-action` step replaces `actions/setup-node` the same way a Python repo's replaces `actions/setup-python`. Declaring tool versions in one file that both local dev and CI read from means they can never drift apart. `jdx/mise-action` (SHA-pinned, per the pinning convention above) runs `mise install` from the repo's `mise.toml` and puts the resolved tools on `PATH`, so subsequent steps just call `uv sync --group dev` / `npm install` directly. When converting an existing pinned-elsewhere version (a hardcoded `actions/setup-node` `node-version:`, a `requirements.txt` pin, etc.) into `mise.toml`, match what's already there rather than picking a newer version yourself — introducing a version bump is a separate change from adding the tool. Apply this even to a repo with no dependencies to install yet (`mise.toml` pinning just the language runtime is still correct) and even to a fork of an externally-maintained repo — the convention isn't limited to `rn-ax`-authored code.
- **Every repo has an `.editorconfig`.** EditorConfig has no remote-extend mechanism (unlike `.github/settings.yml` or the Renovate preset), so this isn't something a repo points at `poppycock` for — copy `poppycock`'s own `.editorconfig` directly into each repo instead.
- **Every repo uses `uv`, not `pip`, for Python dependencies — `[dependency-groups]` in `pyproject.toml`, not the legacy `[tool.uv] dev-dependencies` key** (deprecated; still resolves today but is the wrong one to write in new/updated repos). No `[project]` table is required for `uv sync --group dev` to work in a repo that's a Home Assistant `custom_components/` integration rather than a distributable package — confirmed working with a `pyproject.toml` containing only `[tool.pytest.ini_options]` and `[dependency-groups]`. Commit `uv.lock` for reproducible CI installs.
- **Every repo uses the `poppycock` Renovate preset when it has dependencies to update** (`{"extends": ["github>rn-ax/poppycock"]}` in `renovate.json`) instead of `dependabot.yml` — this org standardizes on Renovate, and running both against the same repo risks duplicate/conflicting update PRs.
- **Every Python repo pins `ruff` in `mise.toml` too, with `[tasks.lint]`/`[tasks.format]` shortcuts (`mise run lint` / `mise run format`) — but never as a CI job.** Linting/formatting is a pre-commit tool, not a merge gate: by the time CI runs, there's no way for it to fix what it finds, so a CI lint failure just blocks a PR on something that was always going to need a local `mise run format` anyway. When adding `ruff` to a repo for the first time, actually run `mise run lint`/`ruff check --fix .` and `ruff format .` and commit the result in the same PR (re-run the test suite after — a `--fix` can occasionally change behavior, e.g. on genuinely dead code) rather than adding the tool and leaving existing findings for later; an unfixed backlog just makes the next real `mise run lint` noisier. The one exception is a repo forked from an external upstream with its own already-curated ruff config (e.g. `ha-healthchecksio`'s `.ruff.toml`) — pin the same `ruff` version the fork already declares elsewhere (e.g. in `requirements.txt`) so `mise run lint` exercises the identical config upstream already tests against, and check what it actually finds before assuming a fix is needed at all; it may already pass clean.
- **New repos with zero commits** can't use a worktree/PR flow yet — there's no branch to fork from. A single minimal bootstrap commit pushed directly to `main` (README, `.gitignore`) is the practical exception, establishing `main` so every commit after that goes through the normal branch+PR workflow. Confirm with the user before the direct push, same as any other case where work would otherwise land on `main` without a PR.
- **Repo-metadata checks reflect the default branch, not the PR branch.** A CI check that validates something via GitHub's own repo API (license detection, topics, etc. — as opposed to reading a file straight out of the checked-out worktree) sees whatever's on `main`, regardless of what the pushed branch itself contains. A repo's first PR that introduces a file one of these checks depends on (e.g. `LICENSE`) will fail that specific check no matter what, purely because `main` doesn't have it yet — this isn't a bug to chase, it resolves itself once the PR merges. Recognize the pattern (the check passes for everything the workspace actually contains, fails only for something that's genuinely repo-wide metadata) rather than repeatedly re-pushing trying to fix it from inside the branch.
