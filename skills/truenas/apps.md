# App-specific notes

Per-app specifics for how each TrueNAS app is actually configured and run — not general Apps/Docker architecture (see SKILL.md for that). Add a new `##` section per app as it's actually confirmed; don't guess or leave stale placeholder content.

## Windmill

Install form has an "Enable Report Workers" toggle, off by default. It spins up an extra worker joined to the `reports` worker group, pre-loaded with Chromium, for headless-browser tasks (PDF/report rendering, web scraping) — not needed for plain script/flow execution. It's just a worker-group toggle, not a schema choice, so it can be flipped on later from the app config without reinstalling.

Containers and the UID each runs as (check with `docker inspect <container> --format '{{.Config.User}}'`): `postgres`/`postgres_upgrade` run as `999:999` (matching the official Postgres image); `server`, `worker`, `worker-native`, `caddy`, `lsp` all run as `1000:1000`; the install's own `permissions` init container runs as root. The compose project's real name is `ix-windmill`, not `windmill`. The Postgres mount is actually named `postgres-data` (not `postgres`) under `Configuration/windmill/`.

**Known gap, not yet fixed (backups aren't set up yet, revisit before they are):** per the `Configuration`-tree ownership policy in SKILL.md, `apps:apps` should always have at least ACL access to everything under `Configuration`. Right now it doesn't for Postgres — `Configuration/windmill/postgres-data` and its `18/` version subdir are `755` (world-readable), but the real PGDATA one level deeper, `postgres-data/18/docker/`, is `700` owned by `999:999` with no ACL, so `apps` has zero access to the actual database files. Before wiring up backups, grant `apps` a POSIX ACL on that path (e.g. `sudo setfacl -R -m u:apps:rx -d -m u:apps:rx postgres-data/18/docker`) — read-only is enough for backup purposes, no need for write.

**Resolved incident, 2026-09-19/20: install failing with `[EFAULT] Failed 'up' action`.** The generic error in the UI and in `/var/log/app_lifecycle.log` gives no real detail — the log line for a failed install is one giant single line (embedded literal `\n`, not real newlines) containing the entire `docker pull` progress dump, and by the time you read it middleware has already torn the failed containers down, so `docker logs <name>` returns "No such container." To actually see what happened: watch `sudo docker events --filter "label=com.docker.compose.project=ix-<app>"` live during a retry, and the instant a `create` event fires for a container, start `sudo tail -F` on its on-disk log file directly — `/mnt/.ix-apps/docker/containers/<full-container-id>/<full-container-id>-json.log` (from `docker.config`'s `data-root`) — rather than trying `docker logs -f <id>`; the daemon uses the default `json-file` log driver (no journald), and the file survives just long enough after container removal for an already-attached `tail -F` to have read it, whereas attaching *after* the "die" event is reliably too late. This technique isn't Windmill-specific — reuse it for any app whose install fails opaquely. (A `pkill -f <pattern>` run over SSH will kill its own SSH session if the invoking command line itself contains the literal pattern text — use a bracket trick like `pkill -f "[w]hatever"` to avoid self-matching.)

## Saltcorn

Not in the TrueNAS catalog (no NocoDB/Windmill-style app definition exists for it) — installed 2026-09-20 as a **Custom App** via `app.create` with `custom_app: true` + a hand-written `custom_compose_config_string` (image `saltcorn/saltcorn:latest` + `postgres:18.6-trixie`), following the general custom-app playbook in SKILL.md.

App-specific quirks beyond the general custom-app gotchas already in SKILL.md:
- The image's `ENTRYPOINT` is the `saltcorn` CLI binary itself with an empty default `CMD` — with no command override it just prints the general CLI help text and exits `0` (looks like a clean exit in `docker ps`, easy to mistake for "it ran fine and stopped" rather than "it never actually started the server"). Needs an explicit `command: ["serve", "--addschema"]` in the compose. `--addschema` auto-creates Saltcorn's DB schema on first boot (otherwise: `error: relation "public._sc_config" does not exist`) and is safe to leave on permanently — a no-op once the schema already exists.
- Runs as root by default (no `USER` in the image) — unlike Windmill/Baserow's non-root containers, so no ACL/ownership dance needed for its own data mount (`/app/data`, via `SALTCORN_FILE_STORE`). Postgres still needs the usual `999:999` ownership on its own mount, same as every other app on this box using the official postgres image.
- First boot redirects `/` to `/auth/create_first_user` — expected, not an error; that's Saltcorn's own admin-account bootstrap flow, not a broken deploy.

Root cause in this case: the "Automatic Permissions" install-form checkbox only fixes ownership for mounts the app catalog explicitly declares (confirmed: just the Postgres data mount, chowned to `999:999`) — it does not know about every mount the app uses. The `Logs/windmill` mounts (`worker-logs`, `worker-cache`, `lsp-cache`, `caddy-data`) were left at the default `apps:apps` (UID 568) ownership, mode `0755` — so the server panicked on startup (`tracing_init.rs`, `PermissionDenied`, Rust exit code 101) trying to write there. Fixed without abandoning the `apps:apps` ownership convention by granting a POSIX ACL instead of chowning — this ZFS mount has `posixacl` enabled: `sudo setfacl -R -m u:1000:rwx -d -m u:1000:rwx <dir>` (the `-d` default ACL makes new files/subdirs the container creates inherit the same grant). Lesson for any future app on this catalog: don't assume "Automatic Permissions" + standard `apps:apps` ownership covers every mount — check what UID each container in the compose actually runs as before assuming the first failure is something else.

**Resolved incident, 2026-09-20: app showed `RUNNING` but `http://truenas.lan:30155/` didn't respond — `caddy` crash-looping.** All other containers were healthy; only `ix-windmill-caddy-1` was `Restarting (1)`, so `app.query` reporting the app as `RUNNING` doesn't mean every container in it is actually up — check `docker ps -a` for the compose project directly when a "running" app isn't reachable. `docker logs` on the crash-looping container (safe to read directly here since it wasn't being torn down, unlike the install-time failures above) showed: `Error: loading initial config: ... provision layer4.handlers.proxy: no upstreams defined`.

Root cause: the catalog's Caddyfile template (`/mnt/.ix-apps/app_configs/<app>/versions/<ver>/templates/macros/caddyfile.conf.jinja`) writes the layer4 SMTP-proxy block as `proxy { upstream <addr> }`, but the pulled `ghcr.io/windmill-labs/caddy-l4:latest` image (confirmed v2.8.4 via `caddy version`) doesn't recognize the `upstream` subdirective in that plugin's Caddyfile syntax — it's silently dropped during `caddy adapt`, leaving the JSON's `layer4.servers.srv0.routes[].handle[]` with `{"handler":"proxy"}` and no `upstreams` key at all. Caddy loads its whole config as one atomic unit, so the broken SMTP block took down the otherwise-fine web UI reverse-proxy block with it. Confirmed reproducible in full isolation (`docker run` the same image against a scratch Caddyfile, no app involved) before touching anything real — worth doing this kind of isolated repro before patching a live app. Tested syntax variants with `caddy adapt` against the real image; this version wants `to <addr>` instead of `upstream <addr>` (a flat inline `proxy <addr>` also works, but `to` is the minimal edit).

Fix: edit `upstream {{ ... }}` → `to {{ ... }}` in the jinja macro file above, then run `sudo midclt call app.redeploy <app_name>` (not `app.start`/`app.stop` — those don't re-render `templates/rendered/docker-compose.yaml` from the macro source, they just replay whatever was already rendered) to force a re-render and container recreation. Confirmed fixed via `curl http://127.0.0.1:30155/health` returning `200 OK` after redeploy. **Caveat:** this patches the locally-cached template for the currently-installed app version — an app version upgrade replaces this file from the catalog fresh, so the bug likely returns and needs re-patching after any Windmill version bump until TrueNAS/windmill-labs fixes it upstream (a matching unresolved report exists on the TrueNAS community forums: "Windmill web ui not available, caddy crashing").
