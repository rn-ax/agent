## Instance

Reachable at `truenas.lan` (`192.168.1.142`) on the home LAN. SSH via the `truenas` alias in `~/.ssh/config` (`ssh truenas`), logged in as `admin` — not `root` or any other user — because `admin` is the one with sudo rights; most real troubleshooting (docker, systemd, zfs) needs sudo, so log in as `admin` from the start rather than discovering the wrong user lacks it partway through.

SSH access is configured via **System → Services → SSH** (Running, Start Automatically enabled) and **Credentials → Local Users → `admin` → SSH Public Key**.

**For an ad-hoc middleware API call from an agent session, use `tn-api <method> [params-json]`** (this skill's own directory) rather than hand-crafting `ssh truenas "sudo midclt call ..."` or juggling a TrueNAS API key — e.g. `tn-api app.query` or `tn-api app.query '[["id","=","portal"]]'`. It wraps the exact same `ssh truenas sudo midclt call` access any admin troubleshooting session already uses, with the method/params shell-quoted safely. This exists because a TrueNAS API key is revocable and gets auto-revoked on "incorrect use" (confirmed 2026-10-01: a key shared with CI's `truenas-deploy` action got revoked mid-session by unrelated API-key debugging, which briefly put that CI pipeline's own credential at risk) — SSH root-via-sudo access has no such revocation risk. This is for interactive/agent-session queries only: a script meant to run unattended on a system with no SSH access of its own (a Windmill job, running in a container) still needs the real websocket+`API_KEY_PLAIN` flow directly, e.g. `rn-ax/windmill`'s `f/truenas/prune_images.py`.

## Apps / Docker architecture

TrueNAS SCALE's "Apps" feature is a `middlewared`-managed wrapper around a real Docker daemon. Key pieces, useful for troubleshooting rather than just clicking around the UI:

- Docker's `data-root` lives on a ZFS dataset, not the boot pool — check `/etc/docker/daemon.json` for the exact path (`Storage/ix-apps/docker` on this box) and `sudo midclt call docker.config` for the pool TrueNAS itself thinks it's using. This matters because that dataset can be affected by anything happening to its underlying pool (a scrub competing for I/O, a pool health issue, etc.) — Docker startup performance and app health are downstream of that pool's health, not independent of it.
- `sudo midclt call app.query` gives the authoritative per-app state (`RUNNING`, `STOPPED`, `DEPLOYING`, ...) as TrueNAS itself tracks it — more useful than raw `sudo docker ps` alone, since it also lists apps that exist but aren't currently running (docker ps only shows what's actually up).
- `sudo midclt call docker.status` is a separate readiness flag (`{"status": "RUNNING"/"FAILED", "description": "..."}`)  distinct from any individual app's state — this is what actually drives the "Applications are not running" banner on the Apps page in the web UI.
- When the exact `midclt` method name isn't known, list what's available rather than guessing: `sudo midclt call core.get_methods` returns every method; pipe through `python3` and filter by prefix (e.g. `name.startswith('app.')`) to find the right one quickly.
- `sudo midclt call core.get_jobs '[["state", "!=", "SUCCESS"]]'` surfaces any stuck/failed async middleware job — useful both for the apps subsystem itself and for spotting unrelated noise (e.g. healthcheck cron jobs failing because the app they ping is down, which looks alarming but is just a downstream symptom, not a separate problem).

**Configuration/Logs dataset convention (user's own setup, not TrueNAS default):** every app gets its own dataset under `/mnt/Storage/Configuration/<app>`, with one **child dataset** (not a plain directory) per mount the app needs (e.g. `cache`, `postgres`, `caddy-data`) — `zfs list -r Storage/Configuration/<app>` shows the real tree; a plain `rm -rf` on the app directory will fail with "Device or resource busy" on each child because they're separate mounted datasets, not directories — use `zfs destroy -r Storage/Configuration/<app>` instead. Any mount that's transient/regeneratable (cache, LSP cache, other data that's fine to lose and gets rebuilt) lives under a mirrored `/mnt/Storage/Logs/<app>/<mount>` dataset instead of under `Configuration` — same one-dataset-per-mount pattern, kept in a separate tree specifically so backup policy can cover `Configuration` while excluding `Logs`. The `Logs` name is a holdover and deliberately covers more than literal log output — the actual criterion for which tree a mount goes in is "does losing this matter," not "is this literally a log." (The June 2025 windmill install predates this refinement and put `cache`/`caddy-data`/`lsp-cache` under `Configuration` — not a pattern to copy for new installs.) Ownership policy differs by tree: `Logs` mounts don't matter — chown/ACL them to whatever UID the container actually needs, no constraint. `Configuration` mounts matter because they need to be backed up: ideally still owned by `apps:apps`; when a container needs a different UID to function (e.g. Postgres needing `999:999`), grant `apps:apps` full access via POSIX ACL rather than leaving it inaccessible — the goal is that whatever eventually does the backup (running as `apps`) can always read everything under `Configuration`, regardless of which UID the container itself needs to own the data as. The `Configuration` dataset is recursively `chown`'d to `apps:apps` by default. Uninstalling an app in the TrueNAS UI does not delete these datasets unless you explicitly choose to remove them — so datasets existing under `Configuration`/`Logs` for an app don't mean that app is currently installed; check `app.query` for actual state. A stateful child dataset (e.g. `postgres`) can retain real data from a prior install long after the app was removed, which can break a fresh reinstall pointed at the same path.

## Installing an app for the user

When asked to install a TrueNAS catalog app end-to-end (not just troubleshoot one already being installed through the UI):

1. **Confirm it's actually in the catalog** — `sudo midclt call app.available '[["name","=","<app>"]]'` returns the real entry (train, version, capabilities) even for apps not in the default "stable" train; check `sudo midclt call catalog.config` for `preferred_trains` if unsure which trains are active. The `apps.truenas.com` website is JS-rendered and unreliable to fetch directly — treat a "not found" from `WebFetch` on that site as inconclusive, not confirmation the app doesn't exist.
2. **Get the real config schema from `truenas/apps` on GitHub**, not the website: `gh api repos/truenas/apps/contents/ix-dev/community/<app>/questions.yaml --jq '.content' | base64 -d` for the full question/value schema (exact nesting to use in `app.create`'s `values`), `.../templates/docker-compose.yaml` for the actual Jinja template, and `.../ix_values.yaml` for consts/default ports/image tags.
3. **Read the compose template for two things before creating datasets**: which UID each container runs as (`set_user(uid,gid)` — a container left at the image default or explicitly root sidesteps the whole UID-mismatch class of problem the Windmill incident in `apps.md` hit; a non-default UID means planning an ACL grant the same way), and which storage mounts are actually persistent (`add_storage(...)` against a real path) versus ephemeral (`"type": "temporary"` — e.g. a Redis cache with no volume at all needs no host dataset whatsoever, don't create one preemptively).
4. **Create the ZFS datasets** per the Configuration/Logs convention above, for persistent mounts only — `Storage/Configuration/<app>/<mount>` as child datasets, `chown -R apps:apps`.
5. **Generate any required secrets** (`openssl rand -base64 <n> | tr -d '/+=' | head -c <len>`) — then see "Handling generated secrets" below before doing anything else with them.
6. **Build the `app.create` payload** matching the schema from step 2 exactly (group → variable nesting), push it to the box, and call `sudo midclt call app.create "$(cat file.json)"` — returns a job id, not a synchronous result.
7. **Poll `core.get_jobs` for that job id** until it leaves `RUNNING`/`WAITING`, then check `sudo docker ps -a --filter "label=com.docker.compose.project=ix-<app>"` for real container health — `app.query`'s own state can read `RUNNING` while one container in the compose project is still crash-looping (see the Windmill caddy incident in `apps.md`), so don't trust the app-level state alone as proof everything actually works.
8. **For an app not in the catalog** (a "Custom App"), there's no schema/template to read — `app.create` instead takes `custom_app: true` plus `custom_compose_config_string` (raw YAML) or `custom_compose_config` (parsed object), with no `permissions` init container and no automatic UID/ownership help at all; own the mount ownership entirely yourself from dataset-creation time. Two gotchas that apply to *any* custom app, not just one specific app: the official `postgres:18+` images expect a single volume mounted at `/var/lib/postgresql` (the image manages a version-numbered subdirectory itself) — mounting at the older `/var/lib/postgresql/data` convention makes the entrypoint refuse to start, complaining about an "unused mount/volume." And **`app.update` does not recreate containers** — same as `app.redeploy` being required after the Windmill Caddyfile fix, changing `custom_compose_config_string` via `app.update` alone leaves the running containers on the old config; always follow with `sudo midclt call app.redeploy <app_name>` to actually apply it (confirm via `docker inspect <container> --format '{{json .Mounts}}'` if in doubt — it shows the *actual* live mount, not what's in the saved config).
9. **If it fails opaquely** (`[EFAULT] Failed 'up' action...`, no real detail in `/var/log/app_lifecycle.log`), reuse the live log-capture technique documented under the Windmill install incident in `apps.md` rather than re-deriving it — it's already written up as a reusable recipe, not just a Windmill-specific fix.

### Handling generated secrets

Any password/key generated during an install gets written to a dated file on `~/Desktop` (e.g. `~/Desktop/<app>-credentials-<date>.txt`) so the user can pull it into their password manager — this is a standing instruction, not a one-off. Tell the user the file is there and that they should delete it once stored; don't delete it proactively, since that assumes they've already done so.

## Resolved incident, 2026-08-23: Apps stuck "Initializing" after a hardware failure/recovery

The box had a hardware failure and came back up, but the Apps page stayed on "Applications are not running" / "Initializing Apps Service" indefinitely. Two distinct problems stacked on top of each other here — worth separating clearly, since fixing the first one doesn't automatically fix the second.

**Problem 1: `dockerd` itself was genuinely stuck, not just slow.** `sudo systemctl status docker` showed `Active: activating (start)` for several minutes, and `sudo journalctl -u docker` showed it hadn't logged anything past `"[graphdriver] trying configured driver: overlay2"` — normally an instant step. Checking the actual process state (`ps -o pid,stat,cmd -p <dockerd_pid>`) showed `D` (uninterruptible sleep, i.e. genuinely blocked on I/O, not just idle or slow), and `sudo zpool status` showed a scrub actively running on the exact pool (`Storage`) that Docker's data-root dataset lives on, issuing hundreds of MB/s. `overlay2` initialization does heavy directory scanning across every image layer, so it was starved competing with the scrub for disk I/O.

Fix: pause the scrub — `sudo zpool scrub -p <pool>` (resume later with `sudo zpool scrub <pool>`, picks up where it left off; check current progress with `sudo zpool status`). Confirmed the process state flip from `D` to `S` within moments, followed by `dockerd` logging lots of `"Removing stale sandbox ..."` / `"Unable to complete atomic operation, key modified, retrying..."` — that's normal cleanup of leftover network state from the earlier unclean shutdown, not an error, and it finishes on its own.

Once `sudo systemctl is-active docker` reports `active` and `sudo docker ps` shows real containers with real uptime, Docker itself has recovered. Apps that were actually `RUNNING` before the crash come back automatically; apps that were `STOPPED` before the crash stay `STOPPED` after recovery — that's correct behavior (TrueNAS restores prior desired state, it doesn't start everything unconditionally), not a sign anything is still broken.

**Problem 2: the UI banner didn't clear even after Docker was fully healthy.** `sudo midclt call docker.status` kept returning `{"status": "FAILED", "description": "Application(s) have failed to start:\nFailed to start docker service"}` — a stale result cached from the original failed startup attempt, not a live check. A hard refresh and a fresh browser tab both did nothing, confirming it's backend state, not a frontend cache. Re-applying the exact same config via `sudo midclt call docker.update '{...}'` (returns a job ID — check outcome with `core.get_jobs`) succeeded but **did not** clear it either, since re-submitting identical config short-circuits without re-running the actual startup/readiness sequence.

Fix: `sudo systemctl restart middlewared` — this is the TrueNAS management daemon/API/UI backend, and restarting it forces a completely fresh readiness check from scratch. Confirmed safe: all containers kept their original uptime across the restart (`middlewared` and `dockerd` are independent processes; restarting the former doesn't touch anything the latter is running). `docker.status` reported `RUNNING` immediately after, and the UI banner cleared.
