# Device notes

Per-device knowledge that isn't visible in the config or entity list itself — behavioural quirks, what a misleadingly-named entity actually means, why a custom entity was built the way it was. Look up the entities themselves in Developer Tools; this file is only the stuff on top. One `##` section per device.

## Traeger smoker

HACS integration `njobrien1006/hass_traeger`; entities are prefixed "Utomhus Smoker".

- **Wifi drops in and out during a cook.** `sensor.utomhus_smoker_grill_state` spends stretches at `unavailable` mid-cook — treat that as "still cooking", don't react to it.
- **`switch.utomhus_smoker_connect`** toggles the integration's MQTT link to the Traeger cloud, nothing on the grill. Off = `client.kill()`, all Traeger entities go `unavailable`; on = (re)connect, and off→on is a force-reconnect. Not to be confused with `sensor.traeger_d8478f9a8842_grill_connected` (the grill's own wifi reaching Traeger).
- **Meat probe unplugged ⇒ `climate.utomhus_smoker_probe_p0` and `sensor.utomhus_smoker_probe_state_p0` go `unavailable`** (the integration surfaces the accessory's `con` flag as entity availability). Gate any probe UI on that rather than on the temperature value — the Probe section of the 🍖 view uses `state_not: [unavailable, unknown]` on the climate entity.
- **Target temps** (`temperature` attribute of the two `climate` entities, °C) are mirrored to `sensor.smoker_target_temperature` / `sensor.smoker_probe_target_temperature` so a chart can plot them as a line — chart cards take entities, not attributes.
- **The 🍖 view's two temp graphs are `custom:apexcharts-card` inside `custom:config-template-card`.** apexcharts is used because the core `history-graph` card won't stretch to fill a container inside a wrapper (leaves whitespace / lets the next section overlap); apexcharts fills it and needs only a fixed `apex_config.chart.height`. The `config-template-card` wrapper is what makes `graph_span` dynamic — a single whole-value `${…}` expression off `sensor.smoker_cook_time` returning e.g. `"3h"` (cook minutes ÷ 60, ceil, min 1). Spritz marks are drawn on the **Smoker** graph only as `apex_config.annotations.xaxis` — a `${…}` function returning one vertical line per past spritz mark (start + 90 min, then every 45).
- **`sensor.traeger_d8478f9a8842_grill_time` is the grill's own wall clock** (always ≈now), not cook duration or start time — the name misleads.
- **Cook duration is computed in `templates.yaml`**, since the integration exposes only the grill clock and the manual countdown timer, not elapsed cook time. `sensor.smoker_cook_started` latches the start (see that file's comments for why `unavailable` is excluded from the trigger); `sensor.smoker_cook_time` counts up from it, with a `formatted` attribute for display because HA has no duration humanizer — a duration sensor's state always renders as the raw number. (`device_class: timestamp` sensors are the one thing the frontend auto-formats, as a live "N hours ago".)
- **Seeding a cook that's already running:** `POST /api/states/sensor.smoker_cook_started` with `{"state": "<iso timestamp>", "attributes": {"device_class": "timestamp"}}`. The manual value holds until the next start trigger fires — but any reload of the template config (`template.reload`, HA restart, editing `templates.yaml`) re-creates the trigger sensor as `unknown` and it stays there until the next real start, so re-seed after those.
- **Interval reminders** both use one pattern: a timestamp sensor holding the *next* mark of the cook, with the reminder automation's `time` trigger pointed *at that entity*, so each time the sensor rolls forward the trigger re-arms itself — no polling. Each sensor's `remaining` attribute is its dashboard countdown.
  - **Pellet refill** (`Smoker · Pellet refill reminder`): `sensor.smoker_next_pellet_check`, every 4h. Badge on the 🍖 view.
  - **Spritz** (`Smoker · Spritz reminder`): `sensor.smoker_next_spritz`, first at 1h30m then every 45m (BBQ best practice — leave the bark to set, then spritz through the stall, stop at the wrap). Spritzes-so-far isn't a sensor — the vertical lines on the Smoker graph show it.
- **`input_boolean.smoker_wrapped`** — user taps "Done spritzing" on the dashboard when the meat goes in foil/paper. While on, `sensor.smoker_next_spritz` is unavailable (so the countdown hides and the spritz automation's trigger disarms); pellet reminders continue. `Smoker · Clear wrapped flag on new cook` turns it back off whenever `sensor.smoker_cook_started` latches a new timestamp.
- **`sensor.utomhus_smoker_heating_state`** is the grill's own assessment of whether it's holding its target, cycling through `idle` → `preheating` → `heating` → `at_temp`, with `over_temp`/`under_temp` when it drifts off target. This is a cloud-pushed enum straight from Traeger, not something this integration computes — and it already has sensible hysteresis: a lid-open-for-spritzing dip doesn't flip it to `under_temp` in practice (confirmed against a real cook on 2026-10-01), so a sustained `under_temp` stretch is a trustworthy "can't hold temperature" signal (e.g. out of pellets) without needing a hand-rolled rate-of-decline calculation on the raw temperature sensor.
- **`binary_sensor.smoker_temperaturlarm`** (`templates.yaml`) is `on` once `heating_state` has read `under_temp` continuously for 10 minutes during a cook (`delay_on`, debounces brief dips), `device_class: problem` for the standard red/ok badge styling. `Smoker · Temperaturlarm` (automation) notifies via `notify.pushover` when it turns on, then re-notifies every 15 min (`time_pattern` + a state condition) while it stays on. The 🍖 view shows it as a badge (visible only while `on`) and as a full-width conditional markdown banner at the top of the view.
- **`sensor.utomhus_smoker_pellet_level`** (`status;pellet_level` straight from the grill, `%`) exists and is wired into the 🍖 view as a badge, but its reliability on this grill is unconfirmed: across every cook in the ~10-day recorder retention (including the 2026-10-01 out-of-pellets cook) it has only ever read `0` or `unavailable`, never a plausible intermediate value — so it's not yet known whether that's an accurate "basically empty" reading or this grill model's hopper sensor just doesn't report real numbers through this integration. Check the official Traeger app's pellet reading against this sensor's next time the hopper is known to be partly full before trusting it enough to alarm on (e.g. `< 15%` sustained, same `delay_on` pattern as the temperature alarm).
